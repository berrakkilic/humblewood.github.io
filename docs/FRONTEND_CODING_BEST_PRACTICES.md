# Frontend Coding Best Practices

Use these rules when writing or reviewing frontend code for The Humblewood Table.
They adapt the maintainable CSS and JavaScript principles in
[front-end-best-practices](https://github.com/ChampiMagic/front-end-best-practices)
to this repository's vanilla TypeScript, generated bundle, and existing DOM style.

## 1. Keep CSS structured and maintainable

- Prefer CSS custom properties for repeated colors, fonts, spacing, radii, and
  shadow values.
- Use descriptive feature-level class names, for example
  `.character-roll-selectors`, `.dice-roll-mode-btn`, or
  `.doodle-corner-panel`.
- Keep modifiers and state classes explicit, such as `.active`, `.hidden`,
  `.dm-private-mode`, or `.sheet-tab-hidden`.
- Reuse existing CSS variables before introducing a new value.
- Do not place many unrelated rules in an arbitrary global block. Group styles
  near their feature section.
- Avoid style-only BEM-like names unless they clarify a real component and are
  used consistently. Existing simple class names are preferable to renaming them
  just for convention.
- Keep the cascade predictable. Avoid `!important`, repeated ID overrides,
  deeply nested selectors, and selectors that depend on a long ancestry.

## 2. Build responsive layouts deliberately

- Test common desktop, tablet, and mobile widths plus unusual intermediate widths.
- Put media queries beside the rules they affect instead of maintaining a second
  copy of the entire stylesheet at the end.
- Prefer `em` or `rem` for breakpoints and user-scalable text sizes when
  introducing new dimensions.
- Use `px` only for precise borders, shadows, media breakpoints, canvas geometry,
  or values that genuinely must remain fixed.
- Use percentages and flex/grid distribution when they help an element remain
  proportional to its container.
- Recheck that toolbar, tab, sheet, dialog, token, and roll controls remain
  usable with long text and narrow widths.
- Never assume desktop-only behavior. Every control should work with touch and
  keyboard input.

## 3. Use a consistent design system

- Reuse tokens for repeated visual values. Add a CSS variable when a value will
  be used by several components or represents a semantic role.
- Preserve the existing parchment, forest, moss, rose, and gold palette.
- Use consistent border widths, radii, spacing scales, and panel shadows.
- Do not create a one-off color, font size, or spacing value when an existing
  class or variable expresses the same purpose.
- State colors should be semantic and consistent: success/normal, warning,
  destructive, private, and inactive states should not swap meanings.

## 4. Use JavaScript for behavior, not layout knowledge

- Prefer CSS for centering, wrapping, stacking, alignment, and responsive layout.
- Use inline JavaScript style changes only for computed state such as drag
  position, measured dimensions, navigation indicators, or canvas coordinates.
- Read layout after DOM changes and batch layout reads before writes.
- Use `requestAnimationFrame` for visual updates that depend on pointer movement,
  resize, scroll, or repeated DOM measurement.
- Avoid storing a CSS layout rule as an imperative DOM calculation if a media
  query or flex/grid rule can express it.

## 5. Follow clean JavaScript practices

- Write focused functions with descriptive names and one clear responsibility.
- Keep new browser code in the appropriate existing file under `frontend/app/`.
- Do not edit `public/app.js`; it is generated by esbuild.
- Avoid large `any` types and vague object parameters. Define the smallest useful
  shape or interface when TypeScript types are stable.
- Avoid repeated casts and defensive workarounds for values the server or state
  already guarantees.
- Keep early guards clear and return before unrelated work.
- Prefer existing helpers for escaping HTML, normalization, rendering, and socket
  communication.
- Do not silently swallow fetch, socket, validation, or persistence failures.

## 6. Separate responsibilities

- Keep feature modules separate:
  state and globals in `state.ts`, routing in `session.ts`, map behavior in
  `map.ts`, characters in `characters/*`, and so on.
- UI event setup should remain close to the feature it controls.
- Socket/network requests, state updates, and DOM rendering should remain
  distinguishable even if one feature currently handles all three.
- Server data and private authorization belong on the server; never rely on
  client-only checks for permissions.
- Keep pure calculations and normalization separate from DOM mutation where
  reuse or testing justifies it.
- Do not split a feature merely to match a framework convention. Add modules
  only when they reduce real complexity or testable boundaries.

## 7. Preserve the shared state model

- Use server-synchronized `state` for shared data and keep data flow predictable.
- UI-only state belongs in the smallest appropriate module variable or element
  state, not in every component or DOM attribute.
- Update shared state from socket events and render the affected UI.
- Do not maintain a second copy of server-owned data unless an explicit
  optimistic or private view requires it.
- Bound temporary lists and logs.
- Keep `bootstrap.ts` last in the build order so socket startup cannot outrun
  handler setup.

## 8. Attach events safely

- Prefer one event setup path per control.
- Rebuild a list and attach handlers to its own elements instead of accumulating
  document-wide listeners.
- Remove timers, observers, animation frames, and listeners when a feature or
  temporary view is destroyed or deactivated.
- Prevent duplicate submissions with pending state and an explicit guard.
- Use `preventDefault` for custom pointer and form behavior only when needed.
- Clean up pointer capture and drag state on cancel/up, not only on success.

## 9. Escape and validate dynamic content

- Escape every server or user-provided string inserted with `innerHTML`.
- Prefer text nodes or existing escaped-template helpers for dynamic names,
  labels, uploads, and descriptions.
- Validate incoming payloads and limits at the server, not only in the browser.
- Preserve safe input values and apply bounds before rendering or persisting.
- Do not interpolate untrusted URLs, CSS values, IDs, or HTML attributes without
  validation and escaping.

## 10. Use tooling consistently

- Use TypeScript and the existing esbuild build rather than introducing a second
  framework or bundler.
- Keep `tsconfig.frontend.json`, generated output, and source imports coherent.
- Run `npm run typecheck:frontend` for type-only work.
- Run `npm run build:frontend` after frontend source changes.
- Run `npm test` before considering a frontend change complete.
- If linting or formatting tooling is added later, configure it repository-wide;
  do not add incompatible per-file formatting conventions.

## 11. Review every frontend change

Before finishing:

- [ ] CSS uses existing variables and feature naming.
- [ ] Layout is checked at narrow, medium, and wide widths.
- [ ] Breakpoints do not overwrite unrelated rules.
- [ ] Primary actions and repeated controls use clear, consistent patterns.
- [ ] Dynamic HTML is escaped.
- [ ] Server-owned state and permissions are not trusted to the browser.
- [ ] Event handlers are attached once and cleaned up where needed.
- [ ] Async failures and repeated submissions have explicit handling.
- [ ] Hot DOM, canvas, timer, socket, and scroll paths are bounded.
- [ ] `public/app.js` was not edited manually.
- [ ] `npm test` passes.
